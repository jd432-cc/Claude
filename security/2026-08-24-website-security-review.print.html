02 · Detail

The findings

Numbered by severity. Findings 1 and 2 are a pair — the second is what turns the first from a bug into working code execution.

01 High Main site Proven

Stored XSS in the Loom Planner

public/tools/loom-planner/ renders its state through innerHTML with unescaped interpolation, and importJSON() accepts a project file with no schema validation. It checks that one top-level key is an array, then hands the whole object to setState():

// js/wiring.js:624
const data = JSON.parse(content);
if (data.connectors && Array.isArray(data.connectors)) setState(data);

From there the file's contents reach eleven sinks unescaped — colour fields dropped straight into style attributes, numeric fields assumed to be numbers, ids written into data- attributes:

js/wiring.js:871, 1027   style="background:${group.colour};color:${T.PAPER};"
js/wiring.js:1224        style="border-left-color:${group.colour};"
js/canbus.js:534         <span class="${dirClass}">${msg.direction}</span>
js/canbus.js:581         data-sig-edit="${sig.id}"
js/utils.js:92, 118      value="${val}"   value="${displayText}"

The escHtml() helper applied elsewhere is itself only correct for element-text context. It escapes <, > and & but not quotes, so it is unsafe inside a quoted attribute even where it is used:

// js/wiring.js:2161 — and the identical copy at js/canbus.js:817
function escHtml(str) {
  const d = document.createElement('div');
  d.textContent = str;
  return d.innerHTML;   // escapes < > & — but NOT " or '
}

Observed — crafted wiring_loom.json, imported through the real UI

window.__XSS_WIREGROUP set : true
window.__XSS_CONNGROUP set : true
injected <img src=x> nodes : 3
XSS EXECUTED               : true

The CAN bus tab falls the same way through #can-import, via msg.direction and sig.id. And because app.js autosaves to localStorage on beforeunload, one import is enough — the payload re-fires on every later visit with no further user action:

Observed — after import, then a plain page load

localStorage keys : [ 'wiring_planner_state', 'canbus_planner_state' ]
XSS re-fires on plain page load (no re-import) : true

A wiring loom or CAN configuration is exactly the kind of file a team passes around. One opened file buys an attacker persistent script execution on theracingdata.com, with access to everything else same-origin — including the other tools' saved sessions.

Fix

  1. Escape for the context. Use an attribute-safe escaper for anything inside a quoted attribute, or set values with setAttribute, textContent and el.style.x = rather than building HTML strings.
  2. Validate on import. Colours against /^#[0-9a-f]{3,8}$/i or a name allowlist; numeric fields through Number(); ids regenerated locally rather than trusted from the file.
  3. Ship the CSP (finding 2) — it contains the damage even when a sink is missed.
02 High Main site Proven

Every per-tool CSP rule is missing

The coming-soon site carries hardened per-tool policies. The main site's _headers is byte-identical up to line 27 and then simply stops — the entire tools section is gone:

$ diff Website-Main/public/_headers Website-ComingSoon/public/_headers
27a28,56
> /tools/report-builder/*
>   Content-Security-Policy: default-src 'none'; script-src 'self'; …
> /tools/loom-planner/*
>   Content-Security-Policy: default-src 'none'; script-src 'self'; …
> /tools/report-builder/templates/*
>   Cache-Control: public, max-age=31536000, immutable

This is the difference between an injection bug and code execution. Replaying the identical finding-1 payload with the coming-soon loom-planner policy applied:

Observed — same payload, coming-soon CSP applied

injected <img src=x> nodes : 3    (HTML injection still happens)
XSS EXECUTED               : false
CSP violations logged      : 3
  e.g. Refused to execute inline event handler because it violates …

Same bug, same payload. The policy stops it dead.

The other four tools have no policy on either site. _headers explains that a new tool "gets no CSP until it is added here; that fails open rather than shipping a blank page." That trade-off costs nothing here — I loaded each unprotected tool under the strictest policy already in use and all four render with zero violations:

ToolDOM nodesCSP violations
/tools/run-plan/82none
/tools/fuel-stint/488none
/tools/event-pack/150none
/tools/load-budget/168none

Fix — restore the section, then extend it

/tools/run-plan/*
/tools/fuel-stint/*
/tools/event-pack/*
/tools/load-budget/*
  Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self';
    font-src 'self'; img-src 'self' data:; connect-src 'self'; form-action 'none';
    base-uri 'none'; frame-ancestors 'none'

Consider inverting the default while you are in the file: a broad /tools/* policy with named exceptions fails closed instead of open.

03 Medium Both sites

Both sites deploy to the same Worker

// Website-Main/wrangler.jsonc AND Website-ComingSoon/wrangler.jsonc — identical
{ "name": "yellow-cake-de51", "compatibility_date": "2026-08-20", … }

Two separate sites, one deployment target. Whichever is published last silently replaces the other, with no warning at deploy time. The coming-soon site is the more hardened of the two and the main site is the one carrying the live tools, so either direction is a bad outcome.

Fix

Give each project its own name.

04 Medium Both sites Proven

No CSP on the marketing pages

_headers documents this as deliberate: "No Content-Security-Policy is set on purpose. […] A CSP without 'unsafe-eval' renders a blank page." I tested that claim against the actual pages. It does not hold.

TestPageResult
Baseline, no CSP/index.htmlrenders — 286 nodes
Candidate with 'unsafe-eval'/index.htmlrenders — 286 nodes, 0 violations
Candidate without 'unsafe-eval'/index.htmlstill renders — 271 nodes, degrades to props only
Candidate + 'unsafe-inline' + blob:/tools/index.htmlrenders — 196 nodes
Candidate/404.htmlrenders — 48 nodes

The page never went blank. The inline <script type="text/x-dc"> block is inert to the browser — unknown MIME type — so it needs no script-src allowance at all. Only support.js, image-slot.js and the unpkg bundles do.

A policy with 'unsafe-eval' is weaker than one without, but far stronger than nothing: it still blocks injected external script sources, <object> and <embed>, <base> hijacking and form exfiltration.

A related dependency. support.js loads React, ReactDOM and Babel from unpkg.com at page load. During testing, with unpkg unreachable, the marketing pages rendered completely blank — zero nodes, zero characters of body text, no fallback. The SRI hashes are pinned and I verified all three against the live upstream files; they match exactly, so integrity is sound. Availability rests entirely on a third-party CDN.

Fix — tested policy for /index.html, /404.html and the design-export pages

default-src 'none'; script-src 'self' 'unsafe-eval' https://unpkg.com;
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com data:; img-src 'self' data: blob:;
connect-src 'self' https://unpkg.com; object-src 'none'; base-uri 'none';
form-action 'none'; frame-ancestors 'none'

/tools/index.html additionally needs 'unsafe-inline' and blob: in script-src. Separately, consider vendoring the three CDN files, as the tools already do for Archivo and docx-templates.

06 Low Coming-soon

The bundled page bypasses SRI

support.js protects its CDN loads with subresource integrity — but the check is skipped whenever a resource override is present:

// public/support.js:1149
function cdnScriptFor(url, sri) {
  const res = window.__resources;
  const v = res ? res[url] : void 0;
  return typeof v === "string" && v
    ? { src: v }          // no integrity on this branch
    : { src: url, integrity: sri };
}

The coming-soon index.html is a self-extracting bundle that decodes React and ReactDOM from embedded base64, turns them into blob URLs, and injects exactly that map:

<script type="__bundler/ext_resources">
[{"id":"https://unpkg.com/react@18.3.1/umd/react.production.min.js",
  "uuid":"38ef6850-b0d7-4866-8497-38cc4b82229b"}, …]

The blobs are same-origin and delivered over TLS, so practical risk is low. But the bundled bytes execute with no verification of any kind, and the SRI hashes that protect the main site do not apply here. If the bundling step is ever compromised, nothing catches it.

Fix

Verify bundled bytes against the pinned hashes before creating the blob URL.

07 Low Both sites Proven

Dev-server containment is a prefix match

const ROOT = path.join(__dirname, 'public');
let file = path.join(ROOT, rel);
if (!file.startsWith(ROOT)) { res.writeHead(403).end('forbidden'); return; }

path.join normalises .., so classic traversal is blocked. But startsWith(ROOT) also accepts any sibling directory whose name begins with public — public.bak, public-secret, public_old:

Observed

$ curl 'http://localhost:8788/..%2fpublic-secret/leak.txt'
SECRET-OUTSIDE-ROOT

$ curl -o /dev/null -w '%{http_code}\n' 'http://localhost:8788/..%2f..%2fetc%2fpasswd'
403

Local preview tooling only, bound to localhost:8788 — but public.bak/ is precisely the sort of directory that accumulates next to a deploy folder.

Fix

const rp = path.relative(ROOT, file);
if (rp.startsWith('..') || path.isAbsolute(rp)) { res.writeHead(403).end('forbidden'); return; }
08 Low Both sites

Message listener has no origin check

public/support.js:1407 accepts messages from any origin. Reachable impact is small — the theme value is validated against "light" and "dark", and X-Frame-Options: DENY stops the site being framed at all.

window.addEventListener("message", (e) => {
  const type = e.data && e.data.type;      // no e.origin check
  if (type === "__dc_theme") { … }
  if (!designDocMode || type !== "__dc_probe") return;
  postDesignMode(designDocMode);
});

Fix

Check e.origin against an allowlist, and replace the "*" targets on the two outbound postMessage calls (lines 1387 and 1858) with a concrete origin.

09 Low Both sites

Resolver reaches prototype properties

_shared/report-engine/resolve.js is a genuinely good piece of design: it replaces docx-templates' JavaScript evaluation with a strict grammar, so a template can never execute code and the page needs no 'unsafe-eval'. One gap — lookup() walks any dotted path, and __proto__, constructor and prototype all match the identifier pattern:

const PATH = /^\$?[A-Za-z_][\w]*(?:\.[A-Za-z_][\w]*)*$/;

A template containing {constructor.constructor} resolves to the Function constructor. The result is only stringified into the document, so this is an information-disclosure edge rather than code execution.

Fix

Reject those three segment names explicitly, and prefer Object.hasOwn(value, key) in the walk.

10 Info Both sites

Transport and isolation headers

Currently set on /*, on both sites: X-Content-Type-Options, Referrer-Policy, X-Frame-Options, Permissions-Policy. Worth adding:

Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Resource-Policy: same-origin

Confirm whether HSTS is already applied at the Cloudflare zone level before adding it here. Permissions-Policy could also deny payment=(), usb=() and serial=().

03 · Clean

What holds up

Worth recording, because several of these are things sites of this kind usually get wrong.

No secrets anywhere

Scans for AWS keys, GitHub and Slack tokens, PEM blocks and credential-shaped assignments came back clean across both trees. No .env, no lockfiles, no npm dependency surface.

SRI hashes are correct

All three pinned sha384 values match the live upstream files byte for byte. The pinning is real, not decorative.

The docx resolver is a real mitigation

Finding 9 notwithstanding. noSandbox is not enabled, and the custom runJs avoids both the iframe and new Function() paths in docx-templates.

The templates are clean

No vbaProject.bin, no OLE objects and no TargetMode="External" references across all 20 .docx templates. No active content in any SVG.

Loom Planner is the outlier, not the pattern

run-plan, event-pack, fuel-stint and load-budget contain zero uses of innerHTML, insertAdjacentHTML, document.write, eval or new Function.

Build and link hygiene

No Invoke-Expression, shell=True or pickle.load in the build and dev scripts. No target="_blank" without rel="noopener", no http:// subresources, no open-redirect patterns.

Tool data stays local

The tools persist to localStorage and export to file. Nothing is transmitted — which is also why finding 1 lands where it does.
